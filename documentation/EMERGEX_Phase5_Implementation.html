5.1 Introduction

5.1.1 Purpose of this phase

The Implementation phase turns the design produced in Phase 4 into a working, verified system. Where Phase 3 established what EMERGEX must do and Phase 4 established how it would be built, this phase documents what was actually built, how it was proven to work, what the proving found, and how the system is installed and run.

The phase has five parts. Section 5.1 states what was delivered. Section 5.2 describes the application's code. Sections 5.3 and 5.4 cover testing — the strategy, and then the test cases, their execution against a dated run, and the defects that execution uncovered. Section 5.5 is the installation procedure.

The outcome that matters most is in 5.4.6. Seven defects were found, and every one of them was predicted by the group's own Phase 3 analysis before any test was written. That chain — a weakness identified during analysis, a correction specified during design, and a failing test that proves the correction is still needed — is the substance of this phase.

5.1.2 What was delivered

EMERGEX is a campus-linked accommodation search and viewing-request system for Richfield students. Richfield operates eight campuses across four provinces and owns no student residences, so students are referred informally to off-campus housing and must assemble a search from classified sites, social media groups and word of mouth. Phase 3 found eight weaknesses in that process, all traceable to one cause: there is no single, campus-linked source of structured and verified accommodation information.

5.2.2 Coding conventions

  • Every database query is a prepared statement. There is no concatenation of user input into SQL anywhere in the codebase.
  • Every variable echoed into HTML passes through e(). Unescaped output is how stored content becomes executable script.
  • Every state-changing POST verifies a CSRF token before doing anything else.
  • Money is stored and calculated in whole rand. The estimator rounds at every step; storing cents would introduce drift between the stored figure and the displayed one.
  • Displayed statistics are derived, never hardcoded. Total beds, inspected count and median walking time are computed on each request.
  • Optional dependencies are wrapped. mbstring is not present in a stock PHP build, so str_len() falls back to strlen() rather than making the form fatal.

5.2.3 Representative modules

Six modules are described below. Between them they cover the connection, the queries, the business logic, the one write path, the main read path and the data layer.

Module 1 — includes/db.php (the connector)

The only file in the project that creates a database connection. It opens one PDO instance lazily, reuses it, and supports MySQL and SQLite behind the same interface.

$pdo = new PDO($dsn, $cfg['username'], $cfg['password'], [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,  // fail loudly
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,                   // real prepares
]);

ATTR_EMULATE_PREPARES => false is the important option. With emulation on, PDO builds the final SQL string itself and only appears parameterised. With it off, parameters travel to the database separately from the statement, so user input can never be parsed as SQL. Test cases TC-45, TC-46 and the injection tests in 5.4 verify the result.

The connector also degrades rather than failing: with no configuration file, or with the server down, db() returns null and the site runs on sample data. A strict flag inverts this once the database is the source of truth.

Module 2 — includes/repository.php (every query)

All SQL in the project lives here. The search query is the most interesting, because its shape varies with the filters while every value remains bound.

$sql    = repo_listing_select() . ' WHERE campus_id = ? AND is_active = 1 AND rent <= ?';
$params = [$campus_id, $max_rent];

if ($types) {
    $sql .= ' AND room_type IN (' . implode(',', array_fill(0, count($types), '?')) . ')';
    $params = array_merge($params, array_values($types));
}

if ($wanted) {
    $in   = implode(',', array_fill(0, count($wanted), '?'));
    $need = (int) count($wanted);          // interpolated, see below

    $sql .= " AND slug IN (
                SELECT listing_slug FROM listing_amenities
                 WHERE amenity_id IN ($in)
                 GROUP BY listing_slug
                HAVING COUNT(DISTINCT amenity_id) = $need
              )";
    $params = array_merge($params, array_values($wanted));
}

Two decisions are worth drawing out. The placeholder lists are built from the count of selected values, never from the values themselves — which is what allows a variable number of filters without concatenating input.

The HAVING count is interpolated rather than bound, and the reason is instructive. With emulation disabled, a bound value arrives as a string; SQLite then compares COUNT(...), an integer, against '2' and never matches, while MySQL coerces and works. That would have been a defect visible on only one of the two supported engines. Interpolating is safe here because the value is count() of a PHP array cast to an integer and can never contain user input. Test case TC-12 verifies the resulting behaviour: amenities are AND, not OR.

Module 3 — includes/functions.php (logic and the seam)

Holds the business calculations and the single branch that satisfies FR10.

function all_listings(): array
{
    static $cache = null;
    if ($cache === null) {
        $cache = using_database() ? repo_listings() : LISTINGS;
        if (!$cache) {
            $cache = LISTINGS;   // connected but the table is empty
        }
    }
    return $cache;
}

Five lookup functions follow this pattern, and every page reads data through them and nothing else. Because both paths return an identically shaped array, the entire presentation layer is unaware of which source answered. That single design choice is what makes "works with no database" a two-line branch rather than a parallel codebase.

The same file holds calculate_payment(), which implements BR-13. The rule that carries the most meaning is in the comment:

// Discounts apply to rent only, never to the deposit or admin fee - a
// deposit is refundable and discounting it would misrepresent what is held.
$discount   = (int) round($gross * $rate);
$rent_total = (int) round($gross - $discount);
$deposit    = (int) round($rent * $deposit_months);
$total      = $rent_total + $deposit + $admin;

Test case TC-26 verifies precisely this by reading the deposit under all three payment plans and requiring the three to be equal.

Module 4 — apply.php (the only write path)

The single place the system accepts data a person typed, and therefore the heaviest test surface in the application. Its order matters: the token is checked before anything else, and the transaction is not opened until every rule has passed.

if (!hash_equals($_SESSION['csrf'] ?? '', (string) ($_POST['csrf'] ?? ''))) {
    $errors['form'] = 'Your session expired. Please try again.';
}

if (str_len($values['fullName']) < 2)                    { $errors['fullName'] = 'Enter your full name'; }
if (!filter_var($values['email'], FILTER_VALIDATE_EMAIL)) { $errors['email']    = 'Enter a valid email address'; }

// South African mobile: 0 or +27, then a 6/7/8 prefix, then 8 digits.
if (!preg_match('/^(?:\+27|0)[6-8][0-9]{8}$/',
                preg_replace('/\s+/', '', $values['phone']))) {
    $errors['phone'] = 'Enter a South African mobile number';
}

if ($values['date'] < date('Y-m-d'))      { $errors['date']  = 'Choose a date that is not in the past'; }
if (str_len($values['notes']) > 500)      { $errors['notes'] = 'Keep it under 500 characters'; }

Errors are collected rather than thrown, so every failing field is reported together and the student's entries are preserved on redisplay. Test cases verify both behaviours.

Three checks are absent from that sequence, and their absence is the substance of three of the seven defects in 5.4.6: there is no maximum length on the name, no check that at least one room was selected, and no check that the selected rooms belong to the selected campus.

Once validation passes, the write is atomic:

return db_transaction(function (PDO $pdo) use ($data, $listing_slugs) {
    $stmt = $pdo->prepare('INSERT INTO viewing_requests (...) VALUES (?,?,?,?,?,?,?,?,?,?)');
    $stmt->execute([...]);
    $id = (int) $pdo->lastInsertId();

    $room = $pdo->prepare('INSERT INTO viewing_request_rooms (request_id, listing_slug) VALUES (?, ?)');
    foreach ($listing_slugs as $slug) {
        $room->execute([$id, $slug]);
    }
    return $id;
});

Both inserts occur inside one transaction, so a request can never be stored without the rooms it names (BR-11). Any exception rolls the whole thing back and the student is told plainly, with the underlying error logged rather than displayed.

Module 5 — search.php (filter validation)

Filter state lives in the URL, so any filtered view is a shareable link. That also means every filter value arrives from the client and must be treated as untrusted.

$campus_id = isset($_GET['campus']) && get_campus($_GET['campus']) ? $_GET['campus'] : DEFAULT_CAMPUS;
$max_rent  = isset($_GET['max'])  ? max(2000, min(9000, (int) $_GET['max'])) : 9000;
$types     = isset($_GET['type'])    ? array_intersect((array) $_GET['type'],    array_keys(all_room_types())) : [];
$wanted    = isset($_GET['amenity']) ? array_intersect((array) $_GET['amenity'], array_keys(all_amenities()))  : [];

Each line is a different validation strategy, chosen to fit the value: the campus must resolve to a real campus or the default is used; the rent is clamped into range rather than rejected, so an edited link still works; and the room-type and amenity lists are intersected against known keys, so an unknown value is simply dropped. Test case TC-10 verifies the clamping at four boundaries.

This is the validation the viewing-request form does not do for its campus and move-in month — the same codebase, two different standards, which is how DEF-04 and DEF-05 came about.

Module 6 — database/schema.mysql.sql (the data layer)

Nine tables in Third Normal Form, with integrity enforced by the database rather than by application code.

CREATE TABLE IF NOT EXISTS `viewing_requests` (

  `reference`      VARCHAR(20)  NOT NULL COMMENT 'RF-YYMMDD-XXXX shown to the student',
  `full_name`      VARCHAR(160) NOT NULL,
  `email`          VARCHAR(190) NOT NULL,

  `move_in_month`  CHAR(7)      NOT NULL COMMENT 'YYYY-MM',
  `notes`          VARCHAR(500) DEFAULT NULL,
  `status`         VARCHAR(20)  NOT NULL DEFAULT 'new',
  `created_at`     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uq_reference` (`reference`),

The UNIQUE constraint on reference is what makes BR-10's uniqueness guarantee real: enforced by the schema rather than only by the code that generates the value. Test case TC-41 verifies it by attempting a duplicate insert and requiring the database to refuse.

The status column is VARCHAR(20) where Phase 4 §4.5.3 specifies an ENUM. That is DEF-06.

5.3 Testing

This section documents the verification of EMERGEX: what was tested, how, with which tools, and on what basis a build is judged fit to demonstrate. Section 5.4 presents the test cases themselves, the results of executing them against a dated run, and the defects that execution uncovered.

5.3.1 Objectives

  1. Verify that every implemented requirement behaves as Phase 3 specified.
  2. Verify that data written through the interface is correct and complete in the database, rather than merely plausible on screen.
  3. Verify that the security controls resist ordinary hostile input.
  4. Establish a repeatable regression suite, so a later change cannot silently undo an earlier fix.
  5. Record every defect found, with enough detail to reproduce and correct it.

5.3.2 Scope

In scope

  • All four pages: landing, search, listing detail, viewing request
  • The complete journey: browse, filter, compare, shortlist, estimate cost, request a viewing, receive a reference
  • All ten functional requirements and all fourteen business rules
  • Security controls: CSRF, injection resistance, output escaping, error disclosure, search-engine exclusion
  • Accessibility and responsiveness at seven viewport widths
  • Behaviour with no database connected

Out of scope

  • Load and performance testing. The prototype runs on one developer machine against eighteen seeded listings; a throughput figure measured there would not be meaningful.
  • Cross-browser testing. Execution used Chromium only.
  • Penetration testing. The security layer verifies that specific controls hold; it is not an adversarial assessment.
  • Assistive-technology testing. Accessibility verification was structural — bound labels, keyboard reachability, live regions — not a screen-reader audit.

The level worth emphasising is integration. A browser test can only prove what a page displays. The change from C# to Python

An earlier version of this suite was written in C# with NUnit and Playwright for .NET. It had to be rebuilt, and the opportunity was taken to reconsider the language. Both parts of that are worth stating plainly.

Why it was rebuilt. Early in the project the group had two prototypes under development. The first test suite was written against one of them; the group subsequently confirmed that the Richfield accommodation interface is the system being delivered. The suite therefore tested an application that was not the deliverable, and was rewritten against the correct one.

This was discovered by the group during Phase 4, with time to correct it, rather than at submission. The test cases were re-derived from the Phase 3 requirements at the same time, which is why every case in this phase carries the requirement it verifies.

Since the suite was being rewritten in any case, four technical reasons favoured Python over C#:

  • No build step. The C# suite had to compile before anything ran. pytest executes the source directly, which materially shortens the edit-run loop when iterating on selectors.
  • Parameterisation is more concise. One @pytest.mark.parametrize turns a single function into eight executions. The NUnit equivalent is considerably more ceremony for identical coverage. Of the 229 tests in this suite, roughly 70 are parameterised expansions of a smaller number of functions.
  • Lower barrier for the group. Python and Visual Studio Code need no Visual Studio installation, so any team member can run the suite.
  • The Playwright knowledge transferred. Locators, web-first assertions and browser contexts work the same way in both, so the move cost the mechanics of rewriting rather than the understanding.

5.3.7 Test design principles

  • No selector appears in a test.
  • No fixed waits. Playwright's assertions retry until a timeout, so there is not one sleep in the suite.
  • Tests clean up after themselves. Every created viewing request is deleted; every altered row is restored.
  • Negative cases are first-class. Roughly half the suite asserts that something is correctly refused. A suite that only proves the happy path proves very little — and every one of the seven defects found lies on a negative path.
  • Integration means the database. Integration tests assert on MySQL rows.
  • Prove derivation, not coincidence. Where a figure is claimed to be computed from data, the test changes the data, reloads, and requires the figure to follow. Matching once could be a number that happened to be correct when it was typed in.
  • Tests that document defects are kept. Seven tests assert correct behaviour the build does not implement and therefore fail. Deleting them would raise the pass rate and conceal seven real defects.

5.4 System Testing

5.4.1 Test case design

Sixty test cases were designed. They are listed in summary in 5.4.4 and in full in Appendix A.

The cases were derived from the requirements rather than from the code. Phase 3 provides ten functional requirements, eight non-functional requirements and fourteen business rules — thirty-two testable statements. Some need more than one case to cover properly, particularly validation, where each field and each boundary needs its own.

Selection was by risk, using four criteria in order: impact if it fails; frequency of use; likelihood of breaking, since conditional logic is where defects cluster; and invisibility, because a missing noindex directive fails silently and automation is the only thing that catches it.

Deriving the cases from requirements rather than from code matters, and it is what produced the result in 5.4.6. A case written by reading apply.php would have tested the validation that is there. A case written from BR-06 — "a viewing request must name at least one listing" — tests the validation that should be there, and fails when it is not.

5.4.2 Case status and execution result

Two distinct pieces of state are tracked for every case, and conflating them is a common source of confusion.

Table 5.4.1 — Case status versus execution result
ConceptWhat it recordsValues used
Case status The lifecycle of the specification — has this case been written, reviewed and agreed? draft → ready → approved

A case can be approved and still fail: approval means the specification is correct, not that the application satisfies it. All sixty cases carry the status approved, and seven of them failed.

Keeping the two separate also preserves history. The result belongs to a particular run, so a case that passes today and fails after tomorrow's change has two results rather than one overwritten value. That is why the test management tool treats runs as a first-class concept rather than storing a single result field on each case.

The defect that matters most

DEF-02 is the significant one, and it is worth setting out in full because it demonstrates what the three phases were for.

Business rule BR-06, written during Phase 3, states that a viewing request must name at least one listing. Phase 3 §3.4.5 finding 1 recorded that the prototype did not enforce it, and identified the risk as "requests the campus cannot act on". Phase 4 §4.6.1 specified the correction — a room-count check before the transaction opens — and Phase 4 Figure 4.15 captured the form showing validation errors on four fields and nothing beside "Rooms to view".

Test case TC-37 asserts the submission is refused. In TR-001 it failed, and the failure produced a stored artefact: reference RF-261101-3591, a complete viewing request with no rooms attached.

A defect predicted during analysis, specified for correction during design, and proven by executed evidence during implementation. That is the thread the three phases were meant to produce.

Why these defects were found

None of the seven would plausibly have been found by manual testing.

A person filling in the form naturally selects a room before submitting, so they would never discover that leaving it empty is accepted. Nobody types a 200-character name by hand. The campus and move-in month are dropdowns, so a person using the interface cannot submit an invalid value — those two were found only because the tests post directly to the server, bypassing the browser entirely.

That last point generalises into the most useful thing this phase established:

Client-side validation is a usability feature. It is never a security control, because the attacker chooses the client.

This was learned the hard way. An early injection test appeared to pass when driven through the interface; investigation showed the browser was refusing to submit the malformed value, so the request never reached PHP. The test was proving that Chromium validates input, not that the application resists injection. Rewritten to post directly, it exercised the server and passed on its merits.

Any security testing conducted exclusively through the interface will report false passes.

Correcting the defects exposed a second problem

The first attempt at TR-002 produced thirty failures, and every one reported the same thing: "All the rooms you select must be at your chosen campus."

The cause was in the tests, not the application. The helper that fills in a valid request selected a room at Umhlanga while leaving the campus field at its default of Bryanston. Before DEF-03 was corrected the application accepted that combination, so the suite had been submitting an impossible request throughout and nothing objected. Enforcing BR-07 made those submissions invalid — correctly — and thirty tests said so within eight minutes. The fixtures were changed to select rooms at the campus being submitted, which is also what a student does.

Two things follow from this, and both are worth more than the defect itself.

The first is that the regression layer demonstrably works. One change to one file, thirty immediate reports, one cause, located in minutes. That is the return on having written the tests, and it is a return that cannot be claimed until something actually changes.

The second is that an unenforced rule can conceal unrealistic test data. The suite was passing while submitting a request no student could make. It passed because the application was wrong in the same direction as the tests. A green run is evidence that the system behaves as the tests expect, which is not the same as evidence that the tests expect the right thing.

Two further findings, in the suite rather than the system

A flaky test. One fixture selected "the campus with the most rooms" using ORDER BY COUNT(*) DESC LIMIT 1. Several campuses hold the same number of rooms, and MySQL is under no obligation to break that tie the same way twice, so the fixture returned different campuses on different runs and a small group of tests passed or failed accordingly. Explicit tie-breaking columns were added. This is recorded because a flaky test is worse than a failing one: a failing test is read, while a flaky test teaches the reader to disregard results.

A false pass. TC-59 continued to fail after the status column had been correctly changed to an ENUM. The test waited for the write to be refused, but MySQL in this environment does not run in strict mode: an invalid enumeration value is coerced to an empty string with a warning rather than rejected. The constraint was working; the test was watching the wrong signal. It now asserts on the value that was actually stored, which gives the same answer on a strict server and on a permissive one.

A second false pass, of the same family. TC-58 originally passed, and should not have. Its assertion accepted any sign of refusal, and the request was being refused — by the database's foreign key, after validation had let the value through. The test was reporting success for exactly the behaviour it existed to detect. It was tightened to distinguish a validation message from the application's generic "we could not save your request", and it then failed, as DEF-05 required. An assertion loose enough to pass for the wrong reason is indistinguishable from no assertion at all.

And one about the environment. Until this point the suite was exercising a copy of the application held directly under htdocs, not the copy inside the repository — the copy that is submitted. The two were almost certainly identical, but nothing kept them so, and an edit to the delivered copy would not have been tested. The base address now points at the repository. Test what you ship, or the suite eventually certifies something nobody receives.

5.4.8 Evaluation of the testing results

Overall assessment

The application is functionally sound and securely implemented. In TR-001, fifty of sixty cases passed, including every case covering search, filtering, listing detail, the shortlist, the cost estimator, submission and persistence. The seven that failed were all corrected, and in TR-002 fifty-seven of sixty cases passed, with none failing and the remaining three recorded as blocked for the reason given in section 5.4.4.

The assessment that follows is written against TR-001, because TR-001 is where the evidence was produced. A clean run states that nothing was found; it is the run that found things which explains what the suite is worth.

The security controls hold, which is worth stating plainly because failures are easier to notice than passes. Six distinct injection payloads were submitted against every search parameter, the listing slug and the form, and each was treated as literal text: no database error was disclosed, no payload acted as a wildcard, and the schema was unchanged. A script tag submitted through the form and a script tag stored in a listing name both rendered as text rather than executing. A submission with its CSRF token removed was refused, as was one with an altered token, while a submission with a valid token succeeded — so the control is effective without being obstructive. No error response disclosed a file path, a stack trace or a SQL error.

The cost estimator is arithmetically correct across all three payment plans, including the rule that carries the most meaning: the discount applies to rent only and never to the deposit or the administration fee. That was verified by reading the deposit under all three plans and requiring the three to be identical.

The write path is sound. Every field survives the round trip unaltered, both tables are written inside one transaction, references are unique and enforced as such by the schema, and the confirmation page claims storage only when a row genuinely exists.

Where the defects cluster

All seven defects lay in one place: the validation sequence of the viewing-request form, and the schema constraint behind it. Nothing was found in the read paths, the calculations, the security controls or the presentation layer — and the corrections in section 5.4.7 touch the same single file, which is the clearest confirmation of the diagnosis.

That concentration is itself a finding. The same codebase validates the search page's filters carefully — the campus must resolve, the rent is clamped, unknown room types and amenities are discarded — while the form's campus and month fields are passed through unchecked. Two different standards in one application, separated by about two hundred lines of code.

The likely reason is that the search filters were written knowing the values come from a URL, while the form fields were written knowing they come from a dropdown. The dropdown constrains the browser, not the request, and that distinction is the root of DEF-04 and DEF-05.

What the suite established beyond finding defects

  • Figures on the landing page are genuinely computed. The test changes a campus bed count, reloads, and requires the displayed total to move by the same amount. A hardcoded number would not.
  • The inspected badge is drawn only from stored data. Setting the flag makes the badge appear; clearing it makes the badge go.
  • Travel times are correct, not merely present. The suite implements the haversine calculation independently and compares.
  • Amenity filtering is AND rather than OR. Proven by requiring the result count to narrow monotonically as amenities are added.
  • Deactivating a listing is a soft delete. The room vanishes from search and its URL returns 404, while the row remains for history.

A note on the suite's own defects

The test suite is software and had its own faults. Four are recorded in section 5.4.7 — a flaky fixture, two assertions that passed for the wrong reason, and a base address pointing at the wrong copy of the application — because they surfaced during the correction cycle rather than during the first run.

They share a shape worth stating on its own. None of them produced a red result. Each made the suite report success it had not earned, and each was found only because something else changed and forced the question. A test that passes for the wrong reason is the hardest fault to notice, because nothing looks wrong — which is why the figures in Table 5.4.10 are reported alongside an account of what the suite got wrong, rather than on their own.

5.4.9 Limitations

  • One browser. Execution used Chromium only; rendering differences in Firefox or Safari would not be detected.
  • Seeded data volumes. Eighteen listings across eight campuses. Pagination, query performance and index effectiveness at realistic volumes are untested.
  • No concurrency testing. The booking transaction has not been tested under simultaneous requests.
  • FR10 not executed in this run. The fallback cases are implemented but were recorded as blocked.
  • Accessibility verification was structural. Bound labels, keyboard reachability and live regions were checked; no screen-reader or colour-contrast audit was performed, so NFR4 is partly rather than fully verified.

5.4.10 Recommendations

The seven defects have been corrected and verified, so the recommendations below concern what should happen next rather than what this phase left undone.

  1. Execute the fallback cases once so FR10 has a recorded result rather than a blocked one. They are implemented and need only a deliberate run, on a copy of the data, with the configuration restored afterwards.
  2. Keep one copy of the application. The duplicate outside the repository has been deleted, and the smoke suite was re-run afterwards to confirm nothing depended on it. The practice is worth keeping: while two copies exist, "it passed" is ambiguous about which one passed.
  3. Run the suite before every submission, not after every change. Eight minutes is short enough to be habitual and long enough that it will be skipped if it is only remembered when something feels wrong.
  4. Validate on the server for every new field. The two defects that reached the database were both a dropdown value trusted because it came from a dropdown. Any field added later will be added the same way unless the rule is written down, which is why it is stated as a principle in section 5.4.6 rather than only as a fix.
  5. Extend coverage where section 5.4.9 says it stops — a second browser, realistic data volumes, concurrent submissions, and an accessibility audit that is more than structural.
  6. Address the outstanding work in Phase 4 §4.8.5 before the system holds any real student's data — rate limiting and moving the application files above the web root being the first two.

5.5.6 Backup and recovery

Reference data is reproducible from seed.php and needs no backup. Captured data — the viewing requests — cannot be reproduced and is the only thing whose loss would matter.

REM Back up
C:\xampp\mysql\bin\mysqldump.exe -u root richfield_accommodation > backup.sql

REM Restore
C:\xampp\mysql\bin\mysql.exe -u root richfield_accommodation < backup.sql

Take a backup before any demonstration. Restoring a dump takes seconds; rebuilding a demonstration state by hand during an assessment does not.

Backups contain personal information and fall under the same retention policy as the live tables. They must never be committed to the repository — .gitignore blocks the obvious filenames, but it cannot stop a rename, so this is a procedural control as much as a technical one.

Conclusion

Phase 5 delivered a working campus-linked accommodation system together with the evidence that it works, and the evidence of where it does not.

The application implements all ten functional requirements across four pages and nineteen files, on a normalised nine-table MySQL schema with integrity enforced by the database rather than by application code. Sixty test cases were derived from the Phase 3 requirements and implemented as 149 test functions producing 230 executions across seven levels, managed in a test tool the group built.

Test run TR-001 executed 224 of those tests on 1 November 2026. Two hundred and seventeen passed, seven failed, and every failure was traced to a documented defect rather than to a fault in the tests. The pass rate was 96.9%, with zero unexplained failures.

The seven defects cluster in one place — the validation sequence of the viewing-request form — and every one of them corresponds to a finding the group recorded in Phase 3 §3.4.5 during data analysis, months before any test was written. Phase 4 specified a correction for each. Phase 5 proved each was still needed, in one case producing a stored viewing request, reference RF-261101-3591, that names no rooms at all.

All seven were then corrected and the suite executed a second time. Test run TR-002 returned 224 passed and none failed, which closes the cycle the three phases describe: a weakness identified during analysis, a correction specified during design, executed evidence that it was still present, and executed evidence that it is gone. The failing tests in TR-001 were never a shortfall in the work. They were its result, and they served as the acceptance criteria for the corrections that followed.

The correction cycle also produced the phase's most useful lesson, and it was not about the application. Enforcing one of the rules made thirty unrelated tests fail, because the suite had been submitting a request no student could make and the application had been accepting it. The suite was passing for the wrong reason. A green run says the system behaves as the tests expect; it does not say the tests expect the right thing — which is why this report sets out what the suite itself got wrong alongside what it found.

The suite is repeatable, self-cleaning and version-controlled alongside the application, so these findings remain protected as development continues.
