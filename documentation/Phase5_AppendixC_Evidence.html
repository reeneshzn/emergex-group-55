Appendix C — Evidence of implementation and testing

This appendix records the test suite as it exists in the repository and as it behaves when executed. Figures C.1 to C.3 show the shared framework; C.4 to C.14 show each of the eleven suite files in turn; C.15 to C.19 show the two runs and their results; C.20 to C.24 show the test management tool; C.25 shows the published repository.

The complete source is published at https://github.com/reeneshzn/emergex-group-55.

C.4 – C.14 · The eleven suite files

One screenshot per file, taken in VS Code. Zoom in two or three notches before capturing: code that cannot be read once the image is scaled to page width evidences nothing.

Figure C.4
suites/00-smoke/test_smoke.py

Figure C.4 — Smoke tests, 15 functions. Run before anything else: every page must return 200, the expected tables must exist, and the seed must have loaded. Roughly ten seconds, so a dead environment is discovered immediately rather than after six minutes of misleading skips.

Figure C.5
suites/01-ui/test_campuses.py

Figure C.5 — Campus and landing page tests, 15 functions (TC-01 to TC-07). Includes the test that changes a bed count and requires the displayed total to move, which distinguishes a computed figure from a hardcoded one that happens to be correct.

Figure C.6
suites/01-ui/test_behaviour.py

Figure C.6 — Accessibility, responsiveness and fallback, 13 functions. Overflow is checked at seven viewport widths by comparing scrollWidth against clientWidth, which is an objective measurement rather than a judgement about a screenshot.

Figure C.7
suites/02-functional/test_search.py

Figure C.7 — Search and filtering, 17 functions (TC-08 to TC-13). Filtering is verified in both directions: every result belongs to the chosen campus, and every row that should appear does appear.

Figure C.8
suites/02-functional/test_listings.py

Figure C.8 — Listing detail, 14 functions (TC-14 to TC-18). The suite implements the haversine calculation independently and compares its own answer with the page's, rather than trusting the application's arithmetic by reading it back.

Figure C.9
suites/02-functional/test_shortlist.py

Figure C.9 — Shortlist, 10 functions (TC-19 to TC-21). The four-room limit is asserted as the application implements it: the control is disabled and explains why, rather than the click being refused.

Figure C.10
suites/02-functional/test_validation.py

Figure C.10 — Form validation, 21 functions (TC-30 to TC-38). The largest file, and the one that found DEF-01, DEF-02 and DEF-03. Every rule is tested from both sides, since a suite that only tests refusals would pass against a form that refuses everything.

Figure C.11
suites/03-logic/test_calculator.py

Figure C.11 — Cost estimator, 13 functions (TC-23 to TC-29). The deposit is read under all three payment plans and required to be identical, which proves the discount never reaches it whatever the rent is.

Figure C.12
suites/04-integration/test_submission.py

Figure C.12 — Persistence, 14 functions (TC-39 to TC-43). Assertions run against MySQL rows, not screen text: a confirmation page would print the same words whether or not the insert succeeded.

Figure C.13
suites/05-security/test_security.py

Figure C.13 — Security, 15 functions (TC-44 to TC-49, TC-57, TC-58). These post directly with requests rather than driving the browser, which is how DEF-04 and DEF-05 were found: both fields are dropdowns, so no amount of clicking could have reached them.

Figure C.14
suites/06-e2e/test_journeys.py

Figure C.14 — End-to-end journeys, 5 functions. Every step is covered individually elsewhere; these exist because covering each step does not prove the path works, and the path is what a student uses.
