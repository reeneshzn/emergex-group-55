EMERGEX — Testing Presentation Brief

Defending your decisions

Phase 5 · Sections 5.3 and 5.4

How to use this

Every question below has three parts. The lead is what you say first — one or two sentences, the direct answer. The depth is what you add if they push. The trap is the weak answer that invites a follow-up you can't win.

The examiner is not testing whether you can recite numbers. They are testing whether the numbers were chosen or whether they just happened. Every answer below shows a decision being made for a reason.

The questions

"Why 118 tests? Where does that number come from?"

118 wasn't a target — it's an output. I designed 36 test cases; 118 is how many executable tests it took to cover them.

A test case is a specification, a test method is one execution. Two things multiply. First, a case whose expected result lists four conditions needs four assertions. Second, a case that specifies several inputs becomes several parameterised runs — my SQL injection case names seven payloads, so it runs seven times from one method. If I'd chosen a number in advance I'd have been padding to hit it, or stopping short of real coverage to stay under it.

Trap: "I wrote 118 because that felt like enough coverage." That invites "so why not 150?" and there's no answer. Always redirect to the 36 — that's where the design decisions live.

"Why those 36 cases? How did you decide what to test?"

Risk-based selection. I ranked everything the system does by what happens if it fails, and tested downward from the worst consequence.

Four criteria, in order:

  1. Impact if it fails. EMERGEX handles deposits and identity documents. A booking that records the wrong deposit, or a document exposed to the wrong person, is the worst thing this system can do — so escrow state transitions and document access got the most coverage.
  2. Frequency of use. Search and booking are what every student does. A defect there affects everyone, so both are covered at UI, functional, integration and end-to-end level.
  3. Likelihood of breaking. Validation, filters and access control are conditional logic with many branches — statistically where defects cluster. Those got negative tests, not just positive ones.
  4. Invisibility. Things that fail silently. A missing security header, an unescaped output, a session that isn't regenerated — nobody notices these in normal use, so automation is the only way they get caught.

I also covered systematically rather than by feel: every user role, every booking path including the declined one, every escrow state transition, and every point where user input reaches the database.

Trap: "I tested all the main features." That's not a method, it's a description. Lead with "risk-based" and name the criteria.

"How do you know 36 is enough? What's your coverage?"

It's enough for the risks I identified, and I've documented what it doesn't cover rather than implying it covers everything.

Exhaustive testing is impossible — that's a basic principle, not an excuse. The property search alone has four filters that combine into dozens of permutations, and testing every one would add almost no information. So the question isn't "is it complete", it's "is what's missing stated". My report lists four explicit limitations: no cross-browser, no load testing, no visual regression, no deep accessibility audit. A marker can then judge the gap deliberately rather than discovering it.

Trap: Claiming full coverage. The next question is always an example you didn't test, and then you've lost the argument.

"Why Playwright and not Selenium?"

Flakiness. Selenium fails the instant an element isn't there; Playwright retries until a timeout. That single difference removed every fixed wait from my suite — there isn't one Thread.Sleep in 118 tests.

In Selenium you write WebDriverWait almost everywhere, and when you forget, the test fails intermittently — passing on a fast machine, failing on a slow one. That's the single biggest cause of distrust in a test suite: once people stop believing a red test, the suite is worthless. Playwright's web-first assertions retry by default, so the flakiness is designed out rather than patched around.

Two practical reasons as well. Playwright manages its own browser binaries, so there's no ChromeDriver version-matching every time Chrome updates. And it gives each test an isolated browser context in milliseconds, which is why 118 tests run in 46 seconds — no session leaks between tests without the cost of a full browser restart.

Trap: "Playwright is newer and more modern." That's not a reason, it's a date. Lead with the flakiness argument — it's concrete and it's true.

"Why C#? Wouldn't Python have been easier?"

Honestly, Python would have been slightly easier to write. I chose C# because the team already works in Visual Studio, and because the language is the least important decision in the whole suite.

The intellectual work is the 36 test cases — what to test and why. Those are identical in any language. What changes is syntax. Playwright's API is nearly the same across C#, Python, Java and JavaScript, so the skills transfer directly. I'd rather defend the test design than the language choice, because the test design is what determines whether defects get found.

I did reconsider partway through, and decided against switching: rewriting 118 working tests would have cost days and gained zero coverage.

Trap: Pretending C# was obviously superior. Conceding that Python is a bit easier and explaining why it didn't matter is a much stronger answer than defending a position you don't hold.

"Why six levels? Isn't that overkill for a prototype?"

Because each level catches a class of defect the others structurally cannot. Integration is the clearest example: a UI test passes when the screen says "deposit held", whether or not the database row was actually written.

That's not hypothetical — it's why I assert against MySQL directly. No real money moves in this system, so the only evidence a deposit was handled correctly is the row. Screen text proves nothing.

The same logic applies to the others. Security is separate because security failures are invisible during normal use — nothing looks wrong when a header is missing. Regression is separate because its job isn't finding new defects, it's proving old fixes still hold. End-to-end is separate because individual features can each work while the journey between them breaks.

Trap: "More levels means better testing." Justify each one by the defect it uniquely catches, or it does look like overkill.

"Why automate at all? It's a prototype — why not just click through it?"

Because manual testing is not repeatable, and because four of my defects require actions no person would perform by hand.

Nobody manually deletes a hidden CSRF token before submitting a form. Nobody copies a stored filename out of the database and requests it in a private window. Nobody sets a property's room count to zero and then tries to book it. Those three actions found three of the four defects.

And repeatability compounds. 46 seconds means the whole suite can run after every change. A manual pass of the same coverage would take hours, so it would be done once, at the end — which is exactly when a defect is most expensive to fix.

"Four tests fail. Why didn't you fix them?"

Because the tests aren't broken — the application is. Each of the four asserts behaviour the system should have and doesn't, so it fails and names the defect in its failure message.

I could delete them and report 100%. That would be dishonest: the defects would still exist, just unrecorded. Leaving them red makes each one an acceptance criterion — when the code is corrected, the test turns green and proves the fix. That's the difference between a test suite and a scoreboard.

Fixing the application code wasn't my role; I own verification, not implementation. Each defect is logged with a severity and a recommended fix for whoever does.

Trap: Sounding apologetic about the 96.6%. This is your strongest moment — say it with confidence.

"How do you know your tests actually work? Who tests the tests?"

A test that cannot fail is worthless, so I verified that mine can. And I caught a real example of one that couldn't.

My SQL injection test appeared to pass when driven through the browser. When I investigated, the sign-in email field is type="email" required — so the browser refused to submit the malformed payload and the request never reached the server. The test was proving that Chromium validates email addresses, not that our code resists injection. I rewrote it to POST directly, bypassing client-side validation, and then it tested the actual PHP.

The general principle: client-side validation is a usability feature and never a security control, because the attacker chooses the client. An attacker uses curl, not your form. Any security test driven only through the UI will report false passes.

Beyond that, four tests fail for known, verified reasons, which demonstrates the suite detects real problems rather than passing everything handed to it.

"What was your most important finding?"

DEF-011. Uploaded identity documents are readable by anyone with the link and no login at all.

Uploads are written to public/uploads, which Apache serves directly, and nothing checks authorisation on retrieval. I uploaded a document as a student, cleared every cookie, requested the file, and got HTTP 200 with the contents.

The filename is forty random hex characters, so it can't be guessed — but that's obscurity, not access control. The URL only has to leak once: a shared screenshot, a Referer header, browser history sync. And for a platform whose entire purpose is protecting students from fraud, storing their ID documents in a public folder undermines the proposition it's built on.

The fix is straightforward: store uploads outside the web root and serve them through a PHP handler that checks the document's owner against the session before sending any bytes.

"Why did you rewrite the original 30 test cases?"

Nine of the original thirty described features the system doesn't have. They weren't failing — they were unrunnable.

They'd been written from an idea of the system rather than the system itself: creating a property listing, hiding a listing as an administrator, a "fully booked" overlay, a payment loading state, webhook synchronisation. None of those exist in the build. I could have reported them as "not automated", but that leaves nine cases of the thirty proving nothing.

So I replaced them with behaviour the system does have and the original set had missed entirely — CSRF enforcement, login throttling, security headers, session hardening, output escaping, audit logging, price tampering. The result is thirty-six cases, all executable, 100% automated.

The lesson is about sequencing: test cases should be written from the requirements specification, alongside it, not from a finished system. That's in my recommendations.

"What would you do differently?"

Two things, and both are in the report rather than invented for the question.

Add data-testid attributes to the markup during development. My page objects currently target CSS classes, so a redesign breaks tests even when behaviour is unchanged. An attribute that exists purely for testing is never edited by accident. It costs nothing while writing the HTML and saves the entire maintenance cost later.

Write the test cases alongside the requirements, not after the build. That's what caused the nine unusable cases, and writing them together would have caught the gap before any automation was written.

Trap: "Nothing, I'd do it the same." Nobody believes it, and it wastes the one question where admitting a limitation makes you look stronger.

"What didn't you test, and why?"

Four things, all deliberate, all documented as limitations.

Cross-browser — Chromium only. Same tests would run on Firefox and WebKit with a configuration change; I prioritised depth on one browser over breadth across three.
Load and performance — meaningless on a single developer machine with four seeded properties. A throughput figure from that environment would be misleading rather than useful.
Visual regression — I assert structure, not appearance. A stylesheet change making every button unreadable would pass all 25 UI tests. Playwright supports screenshot comparison; it was a scope decision.
Deep accessibility — I checked alt text and ARIA roles, which is structural. Colour contrast and real screen-reader behaviour need tooling and human testing I didn't have.

"How does your work connect to the rest of the project?"

Test cases trace back to requirements, and two of my findings feed back into earlier phases.

The V-model: every development phase has a matching test level. Functional requirements from Phase 3 map to end-to-end and functional tests; non-functional requirements map to security and UI; the database design in Phase 4 maps to integration. The traceability matrix is what demonstrates that link — without it, the test cases are just a list.

Going the other way: DEF-010 is a missing data integrity constraint, so it belongs in the Phase 3 data analysis. DEF-011 and DEF-012 are security design concerns for Phase 4. Testing didn't just consume the earlier phases' output — it corrected it.

If you don't know

Say so, then say what you'd do. "I didn't test that — it was out of scope because [reason]. If I had time I'd approach it by [method]." That's a strong answer. Guessing is not, and anyone who knows the subject spots it immediately.
