5.3 Testing

5.3.1 Introduction

This section documents the verification of the EMERGEX student accommodation platform: what was tested, how, with which tools, and on what basis a build is judged fit to demonstrate. Section 5.4 that follows presents the test cases themselves, the results of executing them, and the defects that execution uncovered.

EMERGEX is a web application built in PHP 8 against a MySQL database, served by Apache under XAMPP. It allows students to search verified accommodation, filter by NSFAS accreditation and rent, book instantly or by request, upload NSFAS evidence, and progress a simulated deposit through an escrow model. Landlords respond to booking requests; administrators verify landlords and review uploaded documents. No real funds are processed at any point — the escrow behaviour is demonstrated, not transacted.

That characteristic shapes the testing approach. Because money never moves, the correctness of the state machine around money is the thing that matters: a deposit that is recorded as released when it was never held would be invisible to a user but wrong in the data. Several tests therefore assert on database rows rather than on screen text.

5.3.2 Objectives

  1. Verify that every implemented feature behaves as specified in the functional requirements.
  2. Verify that data written by the application is correct and complete in the database, not merely plausible on screen.
  3. Verify that access controls, input handling and session management resist ordinary hostile input.
  4. Establish an automated regression suite that can be re-run on demand, so a later change cannot silently undo an earlier fix.
  5. Record any defect found, with enough detail to reproduce and fix it.

5.3.3 Scope

In scope

  • All public pages: home, property search, property detail, how-it-works, privacy, sign-in, registration.
  • All three authenticated roles: student, landlord, administrator.
  • The complete booking lifecycle: instant book, request-and-approve, request-and-decline, deposit simulation, check-in confirmation.
  • NSFAS document upload and administrator review.
  • Landlord verification and the audit trail.
  • Security controls: authentication, authorisation, CSRF, session handling, input escaping, upload handling, error disclosure.

Out of scope

  • Load and performance testing. The prototype runs on a single developer machine against seeded data; a throughput figure measured there would not be meaningful.
  • Cross-browser testing. Execution used Chromium only. Firefox and WebKit are supported by the same framework and would require only a configuration change.
  • Real payment integration. None exists to test.
  • Penetration testing. The security layer verifies that specific controls hold; it is not an adversarial assessment.

Playwright was chosen over Selenium for two reasons. Its assertions are web-first: Expect(locator).ToBeVisibleAsync() retries until a timeout rather than failing the instant the element is missing, which removes the explicit waits and arbitrary sleeps that make Selenium suites flaky. Second, it provides an isolated browser context per test at negligible cost, so no session leaks between tests.

5.3.7 Framework architecture

The suite is not a flat collection of scripts. Shared machinery lives in a Support namespace — the test harness — separate from the tests themselves.

Table 5.3.5 — Framework components
ComponentResponsibility
TestConfigBase URL, demo credentials and seeded-data constants in one place. Every value is overridable by environment variable so the suite runs on another machine without code changes.
BaseTestBase class for every test. Provides a fresh browser context, sign-in and sign-out helpers, and a helper that POSTs directly to a handler with a valid CSRF token.
DatabaseParameterised MySQL access used by the integration and security layers, plus cleanup helpers.
TestFilesUpload fixtures built in memory — a minimal valid PDF, a 1×1 PNG, and an inert PHP file used to test disguised uploads. Nothing is checked into the repository.
Pages/Page objects. Every CSS selector in the suite lives here and nowhere else.

Why the Page Object Model matters. Tests express intent — open the listing, start the booking, submit it — while page objects hold the knowledge of which DOM element that means. When the markup changes, the fix is one line in one file rather than a search across ninety tests. It also makes the tests readable to someone who has never seen the HTML.

5.3.8 Test design principles

  • No selector appears in a test. Enforced by convention and visible on inspection.
  • No fixed waits. There is not one Thread.Sleep in the suite. Web-first assertions retry until their timeout.
  • Every test cleans up after itself. Rows created during a test are removed in a finally block or a [TearDown], so the suite is repeatable without reseeding between runs.
  • Negative cases are first-class. Roughly half the suite asserts that something is correctly refused. A suite that only proves the happy path proves very little.
  • Integration means the database. Integration tests assert on MySQL rows, because that is the only way to prove persistence actually happened rather than that a success message was displayed.
  • Tests that document defects are kept. Four tests assert correct behaviour the build does not implement and therefore fail. Deleting them would raise the pass rate and hide four real defects.

5.3.10 Executing the suite

Two execution paths were used, for different purposes.

Visual Studio Test Explorer was used during development. Grouping by trait presents the six levels as folders, individual tests can be re-run in isolation, and failure messages are inspectable in place.

The .NET CLI was used for the recorded run. Test Explorer holds results in memory and does not honour the logger configuration in .runsettings, so it cannot produce a results file. The run of record was therefore executed as:

dotnet test --settings .runsettings

which writes a TRX result file and a browsable HTML report to TestResults/. Individual levels can be run with --filter "Category=Security" and equivalents.

5.4 System Testing

5.4.1 Test case design

Thirty-six test cases were designed, each specifying preconditions, numbered steps, and an expected result. They are listed in summary in section 5.4.2 and in full in Appendix A.

An earlier set of thirty cases was discarded during design. Nine of those thirty described functionality the implemented system does not contain — creating a property listing, hiding a listing as an administrator, a "fully booked" overlay, a payment-processing loading state, webhook payment synchronisation, a declined-payment path, rejecting a landlord's verification, editing a landlord profile, and validating a rent-price field. Retaining them would have produced a report full of untestable cases. They were replaced with cases covering behaviour the system does implement but which the original set had not considered: CSRF enforcement, login throttling, security response headers, session cookie hardening, output escaping, audit logging, randomised upload filenames, and price tampering through request parameters.

On the ratio of cases to test methods. Thirty-six test cases are implemented by 118 automated test executions. This is expected rather than inconsistent. A case whose expected result lists four conditions requires four assertions, and a case that specifies several inputs — four injection payloads, six public pages — becomes several parameterised executions of one method. The test case is the unit of specification; the test method is the unit of execution. Appendix B maps every case to the methods that implement it.

5.4.4 Defects identified

Four defects were identified. All four were found by automated tests; none was visible through ordinary manual use of the application, which is the central argument for the effort invested in the suite.

Table 5.4.4 — Defect register
IDSeverityDescriptionRecommended fix
DEF-011Critical Uploaded identity documents are written to public/uploads and served directly by Apache with no authorisation check. An anonymous request for a document URL returned HTTP 200 and the file contents. The stored filename is forty random hexadecimal characters and cannot be guessed, but an unguessable URL is obscurity, not access control: anyone who obtains the link through a shared screenshot, a Referer header or browser history synchronisation can read another student's identity document without a session. Store uploads outside the web root and serve them through an authenticated PHP handler that checks user_documents.user_id against the current session before streaming bytes.
DEF-010High book.php never reads available_rooms, and no code path decrements it. A property advertising zero available rooms accepts an unlimited number of bookings, while the landlord's dashboard continues to display zero. The column is declared SMALLINT UNSIGNED, so the database cannot store a negative value — but that is a storage constraint, not a business rule, and it is never exercised because nothing writes to the column. Add an availability check inside the existing transaction in book.php, and decrement the column on successful booking.
DEF-012Medium verify_csrf() sets HTTP 419. That code is a Laravel convention and is not registered with IANA, so Apache does not recognise the status line and substitutes 500 Internal Server Error. The CSRF protection itself is effective — the request is refused and no session is issued — but every legitimately blocked submission is reported to the user and to any monitoring as a server crash, and the intended "The form expired" guidance never reaches the page. Return 403 Forbidden from verify_csrf() in bootstrap.php.
DEF-013Low app.js correctly sets the hidden property on the .student-only label when the Landlord role is selected. However app.css declares label { display: block }, and an author stylesheet rule takes precedence over the user-agent rule [hidden] { display: none }. The attribute is therefore set while the field remains visible, so a landlord is shown — and can complete — a student-number field that does not apply to them. Add [hidden] { display: none !important; } to app.css.

5.4.5 Evaluation of the testing results

Overall assessment

The application is functionally sound. All twenty-seven functional, integration and end-to-end cases passed, including every booking journey and every escrow state transition. The core value proposition of the system — that a student can find verified accommodation, book it, and move a deposit through a transparent escrow model — works correctly and persists correct data at every step.

Security is largely well implemented, which is worth stating plainly because the failures are easier to notice than the passes. Database queries are parameterised throughout: seven distinct SQL injection payloads across the search and sign-in interfaces were treated as literal text, with no error disclosure and no authentication bypass. Passwords are hashed. Session identifiers are regenerated on sign-in, preventing session fixation. The session cookie is HttpOnly and SameSite=Lax and is not readable from page script. Security response headers are present. Uploads are validated by content inspection rather than by file extension, and a PHP file declaring an image MIME type was correctly rejected. Output is escaped, so a stored HTML payload rendered as literal text rather than executing.

The significant finding

DEF-011 is the defect that matters. The system's purpose is to protect students from accommodation fraud, and it asks them to upload NSFAS documentation — which for a South African student typically carries an identity number, a name, and financial information. Storing those files in a publicly served directory undermines the trust proposition the platform is built on. The random filename means the exposure requires the URL to leak rather than being enumerable, which lowers the likelihood but not the impact. It is recommended that this be resolved before any demonstration involving real documents.

What automation contributed

None of the four defects would plausibly have been found by manual testing. A tester does not delete a hidden CSRF field before submitting a form; does not copy a stored filename out of the database and request it in a private window; does not set a property's room count to zero and then attempt to book it; and would very likely accept the student-number field as correct because the script governing it is written correctly — only the rendered result is wrong. The value of the suite lies less in confirming that the happy path works than in exercising the paths nobody thinks to try.

A methodological finding

The SQL injection test initially appeared to pass when driven through the user interface. Investigation showed that the sign-in email field is declared type="email" required, so the browser refused to submit the malformed payload and the request never reached the server. The test was proving that Chromium validates email addresses, not that the application resists injection.

The test was rewritten to POST directly, bypassing client-side validation, at which point it exercised the PHP and passed on its merits. The general lesson is that client-side validation is a usability feature and never a security control, because the attacker chooses the client. Security testing conducted exclusively through the interface will report false passes.

Limitations

  • Execution was against Chromium only. Rendering differences in Firefox or Safari would not be detected.
  • The suite runs against seeded data of four properties and three users. Behaviour under realistic data volumes — pagination, query performance, index effectiveness — is untested.
  • No load or concurrency testing was performed. The booking transaction has not been tested for race conditions under simultaneous requests, which is relevant given DEF-010.
  • Accessibility testing was structural (alternative text, ARIA roles, focus order). No assistive-technology or colour-contrast audit was conducted.

5.4.6 Recommendations

  1. Resolve DEF-011 before any demonstration using real documents. Move uploads outside the web root and serve them through an authenticated handler.
  2. Implement the room-availability control (DEF-010) inside the existing booking transaction, and add the corresponding integrity constraint to the data model documented in section 3.4.
  3. Correct the CSRF rejection status (DEF-012) to 403, so blocked submissions are distinguishable from genuine server errors in logs.
  4. Correct the hidden-field rendering (DEF-013) with an explicit [hidden] rule in the stylesheet.
  5. Re-run the suite after each fix. The four failing tests are the acceptance criteria for those fixes; each should turn green without any other test turning red.
  6. Extend the suite as features are added. Nine cases were removed because their features do not exist. If listing creation or administrative moderation is implemented, the corresponding cases should be restored.

5.4.7 Conclusion

Thirty-six test cases were designed from the implemented behaviour of the system and automated as 118 executable tests across six levels. All thirty-six were executed. One hundred and fourteen tests passed, four failed, and every failure was traced to a documented defect rather than to a fault in the tests.

The system is functionally correct and, with one significant exception, securely implemented. The four defects identified are individually addressable, and the tests that revealed them serve as the acceptance criteria for their resolution. The suite is repeatable, self-cleaning and version-controlled alongside the application, so it will continue to protect these findings as development continues.

A.5 Regression

TC-28 — Security Headers and Session Cookie Hardening

Level: Regression · Priority: High · Result: Pass

  1. Request any page and inspect the response headers.
  2. Confirm X-Frame-Options, X-Content-Type-Options, Content-Security-Policy and Referrer-Policy are present and correctly valued.
  3. Sign in and inspect the session cookie attributes.
  4. Read document.cookie from page script and confirm the session cookie is absent.

Expected: X-Frame-Options is DENY, X-Content-Type-Options is nosniff, the CSP includes frame-ancestors 'none', and Referrer-Policy is set. The session cookie is HttpOnly with SameSite=Lax and is not readable from JavaScript.

Appendix B — Reproducing the run

The complete suite and its documentation are held in EMERGEX.Tests/ alongside the application source.

B.1 Prerequisites

  1. Apache and MySQL running under XAMPP.
  2. .NET 9 SDK installed.
  3. Playwright browser binaries installed:
    powershell -ExecutionPolicy Bypass -File bin\Debug\net9.0\playwright.ps1 install chromium

B.2 Procedure

  1. Reset the database to a known state:
    C:\xampp\php\php.exe application\database\install.php
  2. Execute the recorded run:
    dotnet test --settings .runsettings
  3. Collect artefacts from TestResults/: the TRX result file and emergex-test-report.html.

Individual levels may be executed with dotnet test --filter "Category=Security" and the equivalents for UI, Functional, Integration, E2E and Regression.
