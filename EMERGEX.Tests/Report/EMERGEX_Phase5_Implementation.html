5.1 Introduction

5.1.1 Purpose of this phase

The Implementation phase turns the design produced in Phase 4 into a working system. Where earlier phases described what EMERGEX should do and how it should be structured, this phase documents what was actually built, how it was proven to work, and how it is installed and run.

The phase has five parts. Section 5.1 sets out what was delivered and how the work was approached. Section 5.2 describes the code. Sections 5.3 and 5.4 cover testing: the strategy, and then the test cases, their execution and the defects found. Section 5.5 is the installation procedure.

5.1.2 What was implemented

EMERGEX is a web application that connects students with verified accommodation, addressing accommodation fraud through three mechanisms: landlord verification by an administrator, listing verification before publication, and a deposit held in escrow until the student has physically checked in.

Table 5.1.1 — Delivered functionality by role
RoleImplemented capability
Public visitorBrowse published listings; search by city, suburb or nearby institution; filter by NSFAS accreditation, maximum rent and instant-book availability; view listing detail with verification badges
StudentRegister and sign in; book instantly or submit a request; track bookings through their lifecycle; simulate a deposit hold; confirm check-in; upload NSFAS evidence for review
LandlordRegister; view listings; review incoming booking requests within a 12-hour response window; approve or decline
AdministratorVerify landlords; verify and publish listings; review uploaded documents; inspect an audit trail; generate operational reports with CSV export

Alongside the application, an automated test suite of 118 tests across six levels was built to verify it. That suite is a deliverable of this phase in its own right and is described in sections 5.3 and 5.4.

5.1.4 Implementation approach

Development proceeded feature by feature rather than layer by layer: each capability was taken from database schema through to working page before the next was started. This keeps every increment demonstrable and surfaces integration problems early — a schema that cannot support the page is discovered in the same sitting rather than weeks later.

Security was implemented as the application was written, not retrofitted. Prepared statements, output escaping, CSRF tokens and role checks are present in the first version of each handler. Retrofitting security means auditing every line already written, and anything missed stays missed.

A note on sequencing. The prototype was built ahead of the prescribed phase order, and a working system existed before the analysis and design documentation was finalised. This was deliberate, to reduce delivery risk on the most heavily weighted phases.

One consequence is worth stating plainly: defects found during testing have been fed back into the earlier documentation rather than recorded only at the end. The missing room-availability constraint appears in the data integrity discussion, and the document storage weakness in the security design. The phase documents therefore describe the system as it is, including its known faults.

5.1.5 Project boundary

The escrow feature is a simulator. No payment service provider is integrated and no funds move at any point. A production system would require a regulated payment provider together with legal, security, privacy and financial compliance review — none of which is in scope for an academic prototype.

For the same reason, real identity or NSFAS documents must never be uploaded to this system. The upload feature exists to demonstrate the review workflow, and section 5.4.6 records a confirmed weakness in how uploaded files are served.

5.2 Coding

5.2.1 Architecture

EMERGEX uses a page-per-URL model: each user-facing address maps to one PHP file in public/, and every one of those files begins by including a shared bootstrap. The bootstrap establishes the session, sends security headers, exposes the database connection and provides the helper functions every page relies on.

This is deliberately simple. A router and MVC layer would be more elegant, but would also place three layers of indirection between a request and the code that answers it — and the module assesses understanding of that code.

application/
├── app/
│   ├── config/config.php          Database, base URL, upload limits
│   └── includes/

│       └── footer.php             Shared page foot

│   ├── landlord.php               Landlord workflow

Only public/ should be exposed by the web server in a production deployment. Configuration, database scripts and includes sit outside it so they cannot be requested directly.

5.2.2 Coding conventions

  • declare(strict_types=1) in every file. PHP otherwise coerces types silently — a string where an integer was expected becomes 0 rather than an error, which hides bugs.
  • Every database query is a prepared statement. There is no concatenation of user input into SQL anywhere in the codebase.
  • Every variable echoed into HTML passes through e(). Unescaped output is how stored content becomes executable script.
  • Every state-changing POST verifies a CSRF token before doing anything else.
  • Authorisation is checked on the server for every request, never inferred from what the interface chose to display.
  • Money is DECIMAL, never float. Binary floating point cannot represent decimal fractions exactly.

5.2.3 Representative modules

Six modules are described below. Between them they cover configuration and security, the main read path, the main write path, the state machine, the administrative workflow, and the data layer.

Module 1 — app/includes/bootstrap.php

Included first by every page. It configures the session, sends security headers, and provides the shared helpers.

session_name('emergex_session');
session_set_cookie_params([
    'httponly' => true,                                  // not readable from JavaScript
    'secure'   => !empty($_SERVER['HTTPS']) && $_SERVER['HTTPS'] !== 'off',
    'samesite' => 'Lax',                                 // not sent on cross-site POSTs
    'path'     => '/',
]);
session_start();

header('X-Frame-Options: DENY');                         // anti-clickjacking
header('X-Content-Type-Options: nosniff');               // no content-type guessing
header('Referrer-Policy: strict-origin-when-cross-origin');
header("Content-Security-Policy: default-src 'self'; ... frame-ancestors 'none'");

The PDO connection is created once and reused through a static variable, with three options that matter:

$pdo = new PDO($dsn, $db['user'], $db['password'], [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,  // fail loudly, never silently
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,                   // real prepares
]);

ATTR_EMULATE_PREPARES => false is the important one. With emulation on, PDO builds the final SQL string itself and only appears parameterised. With it off, parameters travel to MySQL separately from the statement, so user input can never be parsed as SQL.

The file also provides csrf_token(), verify_csrf(), e(), require_auth(), audit(), money() and the login throttle.

Module 2 — public/properties.php (search)

The main read path. Filters build a parameterised WHERE clause: the shape of the query varies with the filters chosen, but every value supplied by the user is bound rather than interpolated.

$where  = ["p.status = 'published'", 'p.verified_at IS NOT NULL'];
$params = [];

if ($keyword !== '') {
    $where[]  = '(p.city LIKE ? OR p.suburb LIKE ? OR p.near_institution LIKE ?)';
    $like     = '%' . $keyword . '%';
    $params[] = $like; $params[] = $like; $params[] = $like;
}
if ($maxRent > 0) { $where[] = 'p.monthly_rent <= ?'; $params[] = $maxRent; }
if ($nsfasOnly)   { $where[] = 'p.nsfas_accredited = 1'; }

$stmt = db()->prepare('SELECT ... WHERE ' . implode(' AND ', $where) . ' ORDER BY ...');
$stmt->execute($params);

The two conditions always present — status = 'published' and verified_at IS NOT NULL — enforce at query level that unverified or unpublished listings can never reach a visitor, whatever filters are supplied.

Module 3 — public/book.php (booking creation)

The main write path, and the clearest example of a transaction. A booking and its escrow record must both exist or neither must.

$pdo = db();
$pdo->beginTransaction();
try {
    $status   = $property['instant_book'] ? 'approved' : 'pending';
    $deadline = $property['instant_book'] ? null
              : (new DateTimeImmutable('+12 hours'))->format('Y-m-d H:i:s');

    $insert = $pdo->prepare('INSERT INTO bookings
        (property_id, student_id, move_in_date, message,
         monthly_rent, deposit_amount, status, response_deadline, created_at)
        VALUES (?, ?, ?, ?, ?, ?, ?, ?, NOW())');

    // Money comes from the property row, never from the request.
    $insert->execute([$propertyId, $user['id'], $moveIn, $message,
        $property['monthly_rent'], $property['deposit_amount'], $status, $deadline]);

    $bookingId = (int) $pdo->lastInsertId();

    $escrow = $pdo->prepare('INSERT INTO escrow_transactions
        (booking_id, amount, status, created_at) VALUES (?, ?, "not_paid", NOW())');
    $escrow->execute([$bookingId, $property['deposit_amount']]);

    $pdo->commit();
    audit('booking.created', 'booking', $bookingId);
} catch (Throwable $exception) {
    $pdo->rollBack();
    $errors[] = 'The booking could not be created. Please try again.';
}

Two decisions are worth drawing out. Rent and deposit are read from the property row, not from the submitted form — a tampered price field has no effect, verified by test case TC-30. The caught exception produces a generic message; the underlying error is never shown, because database errors disclose table and column names.

Module 4 — public/dashboard.php (escrow state machine)

The student dashboard advances the escrow simulation. Every action re-queries the booking joined to the current user, so ownership is proven by the query rather than assumed:

$stmt = db()->prepare('SELECT b.*, e.id AS escrow_id, e.status AS escrow_status
    FROM bookings b
    JOIN escrow_transactions e ON e.booking_id = b.id
    WHERE b.id = ? AND b.student_id = ?');          // ownership enforced here
$stmt->execute([$bookingId, $user['id']]);
$booking = $stmt->fetch();

if (!$booking) { http_response_code(404); exit('Booking not found.'); }

A booking belonging to someone else returns 404, not 403. That is intentional: 403 would confirm the booking exists, telling an attacker that a given identifier is real. 404 reveals nothing. Test case TC-33 verifies this.

The same file handles NSFAS uploads, validating by content rather than by file name:

$mime = (new finfo(FILEINFO_MIME_TYPE))->file($file['tmp_name']);   // inspect the bytes

if (!in_array($mime, config('uploads.allowed_mime'), true)) {
    flash('error', 'Only PDF, JPG and PNG files are accepted.');
} else {
    $extension = match ($mime) {                        // extension from content
        'application/pdf' => 'pdf',
        'image/jpeg'      => 'jpg',
        'image/png'       => 'png',
    };
    $stored = bin2hex(random_bytes(20)) . '.' . $extension;   // unguessable name
    move_uploaded_file($file['tmp_name'], $target);
}

The client-supplied file name never builds the storage path, which is why a name containing directory traversal sequences has no effect (TC-34).

Module 5 — public/admin.php (verification and audit)

verify_csrf();
$action   = (string) ($_POST['action'] ?? '');
$entityId = filter_input(INPUT_POST, 'entity_id', FILTER_VALIDATE_INT);

if ($action === 'verify_user') {
    db()->prepare('UPDATE users SET verified_at = NOW()
                   WHERE id = ? AND role = "landlord"')->execute([$entityId]);
    audit('admin.user_verified', 'user', $entityId);
    flash('success', 'Landlord verified.');
}

AND role = "landlord" in the UPDATE is a second line of defence: even if a non-landlord identifier were submitted, no row would match. Narrowing the write at query level is more reliable than checking first and updating afterwards.

The audit trail survives deletion of the acting user — the foreign key uses ON DELETE SET NULL rather than cascade — because a record of who approved what must outlive the account.

Module 6 — database/schema.sql (data layer)

Seven tables in Third Normal Form, with integrity enforced by the database rather than by application code: eight foreign keys with deletion behaviour chosen per relationship, ENUM domains, CHECK constraints on monetary values, and composite indexes aligned to actual query patterns.

CREATE TABLE escrow_transactions (
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    booking_id  BIGINT UNSIGNED NOT NULL UNIQUE,     -- UNIQUE enforces one escrow per booking
    amount      DECIMAL(10,2) NOT NULL,              -- never FLOAT for money
    status      ENUM('not_paid','held','released','refunded') NOT NULL DEFAULT 'not_paid',
    reference_code VARCHAR(40) NULL UNIQUE,
    CONSTRAINT fk_escrow_booking FOREIGN KEY (booking_id)
        REFERENCES bookings(id) ON DELETE CASCADE,
    CONSTRAINT chk_escrow_amount CHECK (amount >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

The UNIQUE on booking_id is what makes the one-to-one relationship real. Without it the relationship would exist only as an intention in application code, and a second escrow row for the same booking would be accepted.

5.3 Testing

This section documents the verification of EMERGEX: what was tested, how, with which tools, and on what basis a build is judged fit to demonstrate. Section 5.4 presents the test cases themselves, the results of executing them, and the defects that execution uncovered.

Because no real money moves, the correctness of the state machine around money is what matters: a deposit recorded as released when it was never held would be invisible to a user but wrong in the data. Several tests therefore assert on database rows rather than on screen text.

5.3.1 Objectives

  1. Verify that every implemented feature behaves as specified.
  2. Verify that data written by the application is correct and complete in the database, not merely plausible on screen.
  3. Verify that access controls, input handling and session management resist ordinary hostile input.
  4. Establish an automated regression suite that can be re-run on demand, so a later change cannot silently undo an earlier fix.
  5. Record any defect found, with enough detail to reproduce and fix it.

5.3.2 Scope

In scope

  • All public pages: home, search, listing detail, how-it-works, privacy, sign-in, registration
  • All three authenticated roles
  • The complete booking lifecycle: instant book, request-and-approve, request-and-decline, deposit simulation, check-in confirmation
  • NSFAS document upload and administrator review
  • Landlord verification and the audit trail
  • Security controls: authentication, authorisation, CSRF, session handling, input escaping, upload handling, error disclosure

Out of scope

  • Load and performance testing. The prototype runs on a single developer machine against seeded data; a throughput figure measured there would not be meaningful.
  • Cross-browser testing. Execution used Chromium only.
  • Real payment integration. None exists to test.
  • Penetration testing. The security layer verifies that specific controls hold; it is not an adversarial assessment.

Playwright was chosen over Selenium for two reasons. Its assertions are web-first: Expect(locator).ToBeVisibleAsync() retries until a timeout rather than failing the instant an element is missing, which removes the explicit waits and arbitrary sleeps that make Selenium suites flaky. Second, it provides an isolated browser context per test at negligible cost, so no session leaks between tests.

5.3.6 Framework architecture

The suite is not a flat collection of scripts. Shared machinery lives in a Support namespace — the test harness — separate from the tests themselves.

Table 5.3.5 — Framework components
ComponentResponsibility
TestConfigBase URL, demo credentials and seeded-data constants in one place. Every value is overridable by environment variable so the suite runs on another machine without code changes.
BaseTestBase class for every test. Provides a fresh browser context, sign-in and sign-out helpers, and a helper that POSTs directly to a handler with a valid CSRF token.
DatabaseParameterised MySQL access used by the integration and security layers, plus cleanup helpers.
TestFilesUpload fixtures built in memory — a minimal valid PDF, a 1×1 PNG, and an inert PHP file used to test disguised uploads.
Pages/Page objects. Every CSS selector in the suite lives here and nowhere else.

Why the Page Object Model matters. Tests express intent — open the listing, start the booking, submit it — while page objects hold the knowledge of which DOM element that means. When the markup changes, the fix is one line in one file rather than a search across ninety tests. It also makes tests readable to someone who has never seen the HTML.

5.3.7 Test design principles

  • No selector appears in a test.
  • No fixed waits. There is not one Thread.Sleep in the suite.
  • Every test cleans up after itself, so the suite is repeatable without reseeding between runs.
  • Negative cases are first-class. Roughly half the suite asserts that something is correctly refused. A suite that only proves the happy path proves very little.
  • Integration means the database. Integration tests assert on MySQL rows, the only way to prove persistence actually happened.
  • Tests that document defects are kept. Four tests assert correct behaviour the build does not implement and therefore fail. Deleting them would raise the pass rate and hide four real defects.

5.4 System Testing

5.4.1 Test case design

Thirty-six test cases were designed, each specifying preconditions, numbered steps, and an expected result. They are listed in summary in section 5.4.4 and in full in Appendix A.

Cases were selected by risk rather than by feature list, using four criteria in order: impact if it fails (deposits and identity documents rank highest), frequency of use (search and booking affect every user), likelihood of breaking (validation, filters and access control are conditional logic, where defects cluster), and invisibility (a missing security header fails silently, so automation is the only way it is caught).

An earlier set of thirty cases was discarded during design. Nine of those thirty described functionality the implemented system does not contain — creating a property listing, hiding a listing as an administrator, a "fully booked" overlay, a payment-processing loading state, webhook payment synchronisation, a declined-payment path, rejecting a landlord's verification, editing a landlord profile, and validating a rent-price field. Retaining them would have produced a report full of untestable cases. They were replaced with cases covering behaviour the system does implement but which the original set had not considered: CSRF enforcement, login throttling, security response headers, session cookie hardening, output escaping, audit logging, randomised upload filenames, and price tampering through request parameters.

On the ratio of cases to test methods. Thirty-six test cases are implemented by 118 automated test executions. This is expected rather than inconsistent. A case whose expected result lists four conditions requires four assertions, and a case specifying several inputs — four injection payloads, six public pages — becomes several parameterised executions of one method. The test case is the unit of specification; the test method is the unit of execution.

5.4.2 Case status and execution result

Two distinct pieces of state are tracked for every test case, and conflating them is a common source of confusion.

Table 5.4.1 — Case status versus execution result
ConceptWhat it recordsValues used
Case status The lifecycle of the specification — has this case been written, reviewed and agreed? draft → ready → approved
Execution result What happened the last time the case was run passed, failed, blocked, not run

A case can be approved and still fail: approval means the specification is correct, not that the application satisfies it. Keeping the two separate also preserves history — the result belongs to a particular run, so a case that passes today and fails after tomorrow's change has two results, not one overwritten value.

All 36 cases carry the status approved.

5.4.6 Defects identified

Four defects were identified. All four were found by automated tests; none was visible through ordinary manual use of the application, which is the central argument for the effort invested in the suite.

Table 5.4.6 — Defect register
IDSeverityDescriptionRecommended fix
DEF-011Critical Uploaded identity documents are written to public/uploads and served directly by Apache with no authorisation check. An anonymous request for a document URL returned HTTP 200 and the file contents. The stored filename is forty random hexadecimal characters and cannot be guessed, but an unguessable URL is obscurity, not access control: anyone who obtains the link through a shared screenshot, a Referer header or browser history synchronisation can read another student's identity document without a session. Store uploads outside the web root and serve them through an authenticated PHP handler that checks user_documents.user_id against the current session before streaming bytes.
DEF-010High book.php never reads available_rooms, and no code path decrements it. A property advertising zero available rooms accepts an unlimited number of bookings, while the landlord's dashboard continues to display zero. The column is declared SMALLINT UNSIGNED, so the database cannot store a negative value — but that is a storage constraint, not a business rule, and it is never exercised because nothing writes to the column. Add an availability check inside the existing transaction in book.php, and decrement the column on successful booking.
DEF-012Medium verify_csrf() sets HTTP 419. That code is a framework convention and is not registered with IANA, so Apache does not recognise the status line and substitutes 500 Internal Server Error. The CSRF protection itself is effective — the request is refused and no session is issued — but every legitimately blocked submission is reported to the user and to any monitoring as a server crash, and the intended "The form expired" guidance never reaches the page. Return 403 Forbidden from verify_csrf() in bootstrap.php.
DEF-013Low app.js correctly sets the hidden property on the .student-only label when the Landlord role is selected. However app.css declares label { display: block }, and an author stylesheet rule takes precedence over the user-agent rule [hidden] { display: none }. The attribute is therefore set while the field remains visible, so a landlord is shown — and can complete — a student-number field that does not apply to them. Add [hidden] { display: none !important; } to app.css.

5.4.7 Evaluation of the testing results

Overall assessment

The application is functionally sound. All twenty-seven functional, integration and end-to-end cases passed, including every booking journey and every escrow state transition. The core value proposition — that a student can find verified accommodation, book it, and move a deposit through a transparent escrow model — works correctly and persists correct data at every step.

Security is largely well implemented, which is worth stating plainly because failures are easier to notice than passes. Database queries are parameterised throughout: seven distinct SQL injection payloads across the search and sign-in interfaces were treated as literal text, with no error disclosure and no authentication bypass. Passwords are hashed. Session identifiers are regenerated on sign-in, preventing session fixation. The session cookie is HttpOnly and SameSite=Lax and is not readable from page script. Security response headers are present. Uploads are validated by content inspection rather than by file extension, and a PHP file declaring an image MIME type was correctly rejected. Output is escaped, so a stored HTML payload rendered as literal text rather than executing.

The significant finding

DEF-011 is the defect that matters. The system's purpose is to protect students from accommodation fraud, and it asks them to upload NSFAS documentation — which for a South African student typically carries an identity number, a name, and financial information. Storing those files in a publicly served directory undermines the trust proposition the platform is built on. The random filename means the exposure requires the URL to leak rather than being enumerable, which lowers the likelihood but not the impact. It is recommended that this be resolved before any demonstration involving real documents.

What automation contributed

None of the four defects would plausibly have been found by manual testing. A tester does not delete a hidden CSRF field before submitting a form; does not copy a stored filename out of the database and request it in a private window; does not set a property's room count to zero and then attempt to book it; and would very likely accept the student-number field as correct, because the script governing it is written correctly — only the rendered result is wrong. The value of the suite lies less in confirming that the happy path works than in exercising the paths nobody thinks to try.

A methodological finding

The SQL injection test initially appeared to pass when driven through the user interface. Investigation showed that the sign-in email field is declared type="email" required, so the browser refused to submit the malformed payload and the request never reached the server. The test was proving that Chromium validates email addresses, not that the application resists injection.

The test was rewritten to POST directly, bypassing client-side validation, at which point it exercised the PHP and passed on its merits. The general lesson is that client-side validation is a usability feature and never a security control, because the attacker chooses the client. Security testing conducted exclusively through the interface will report false passes.

5.4.8 Limitations

  • Execution was against Chromium only. Rendering differences in Firefox or Safari would not be detected.
  • The suite runs against seeded data of four properties and three users. Behaviour under realistic data volumes — pagination, query performance, index effectiveness — is untested.
  • No load or concurrency testing was performed. The booking transaction has not been tested for race conditions under simultaneous requests, which is relevant given DEF-010.
  • Accessibility testing was structural (alternative text, ARIA roles, focus order). No assistive-technology or colour-contrast audit was conducted.

5.4.9 Recommendations

  1. Resolve DEF-011 before any demonstration using real documents. Move uploads outside the web root and serve them through an authenticated handler.
  2. Implement the room-availability control (DEF-010) inside the existing booking transaction, and add the corresponding integrity constraint to the data model.
  3. Correct the CSRF rejection status (DEF-012) to 403, so blocked submissions are distinguishable from genuine server errors in logs.
  4. Correct the hidden-field rendering (DEF-013) with an explicit [hidden] rule in the stylesheet.
  5. Re-run the suite after each fix. The four failing tests are the acceptance criteria for those fixes; each should turn green without any other test turning red.
  6. Extend the suite as features are added. Nine cases were removed because their features do not exist. If listing creation or administrative moderation is implemented, the corresponding cases should be restored.

5.5.6 Resetting and backing up

Reset. Re-running install.php drops and recreates every table before reseeding. This is the quickest way to return a demonstration to a known state. It destroys all data, so anything worth keeping must be backed up first.

Backup:

C:\xampp\mysql\bin\mysqldump.exe -u root emergex > emergex_backup.sql

Restore:

C:\xampp\mysql\bin\mysql.exe -u root emergex < emergex_backup.sql

Take a backup before any demonstration. Restoring a dump takes seconds; rebuilding a demonstration state by hand during an assessment does not.

5.5.7 Deployment considerations

The procedure above describes a local assessment environment. A production deployment would additionally require: HTTPS, so that the secure session cookie flag takes effect; a database user with only the privileges the application needs, rather than root; the document storage weakness (DEF-011) resolved; a web server configured to expose only the public directory; and error display disabled with logging to file.

None of these is in scope for the prototype, but all are prerequisites before the system could handle real student data.

Conclusion

Phase 5 delivered a working student accommodation platform together with the evidence that it works. The application implements verified listings, two booking paths, a simulated escrow lifecycle, document review and an audit trail across three user roles, built on a normalised MySQL schema with integrity enforced by the database.

Thirty-six test cases were designed from the implemented behaviour of the system and automated as 118 executable tests across six levels. All thirty-six were executed in a single recorded run. One hundred and fourteen tests passed, four failed, and every failure was traced to a documented defect rather than to a fault in the tests.

The system is functionally correct and, with one significant exception, securely implemented. The four defects identified are individually addressable, and the tests that revealed them serve as the acceptance criteria for their resolution. The suite is repeatable, self-cleaning and version-controlled alongside the application, so it will continue to protect these findings as development continues.

  3. Request the uploads directory itself and inspect the response.
  4. Register a second student and POST a deposit action naming the first student's booking id.
  5. Re-query the first student's escrow row.

Expected: The anonymous document request is refused. The uploads directory returns 403 or 404. The cross-account booking action returns HTTP 404 and the victim's escrow row is unchanged.
Actual: The cross-account and directory-listing controls hold. The anonymous document request returned HTTP 200 with the file contents — see DEF-011.

TC-34 — Harden File Upload Handling

Level: Security · Priority: High · Result: Pass · OWASP: A03 / A04

  1. Upload a valid PDF whose filename contains directory traversal sequences.
  2. Read the stored_name and original_name columns for that upload.
  3. Upload a file containing PHP source but declaring a PDF MIME type.
  4. Confirm the response and check whether a row was created.

Expected: The stored name is 40 random hex characters plus an extension derived from the sniffed MIME type, with no traversal sequences or path separators. The disguised PHP file is rejected and no row is created.

TC-35 — Protect Session Transport and Prevent Caching

Level: Security · Priority: High · Result: Pass · OWASP: A05

  1. Record every request URL issued during a signed-in browsing session.
  2. Search those URLs for a session identifier parameter.
  3. Request the student dashboard and inspect its Cache-Control header.

Expected: No request URL contains a session identifier. The dashboard sends a Cache-Control header including no-store or no-cache.

TC-36 — Suppress Internal Detail in Error Responses

Level: Security · Priority: Medium · Result: Pass · OWASP: A05

  1. Request a property detail page for an id that does not exist.
  2. Request a property detail page with a non-numeric id.
  3. Request a booking page with a negative property id.
  4. Request a page that does not exist.
  5. Inspect each response body for internal detail.

Expected: No response contains a server file path, "Stack trace", "SQLSTATE", or a PHP Warning, Notice or Deprecated message.

Appendix B — Reproducing the test run

The complete suite and its documentation are held in EMERGEX.Tests/ alongside the application source.

B.1 Prerequisites

  1. Apache and MySQL running under XAMPP.
  2. .NET 9 SDK installed.
  3. Playwright browser binaries installed:
    powershell -ExecutionPolicy Bypass -File bin\Debug\net9.0\playwright.ps1 install chromium

B.2 Procedure

  1. Reset the database to a known state:
    C:\xampp\php\php.exe application\database\install.php
  2. Execute the recorded run:
    dotnet test --settings .runsettings
  3. Collect artefacts from TestResults/: the TRX result file and emergex-test-report.html.

Individual levels may be executed with dotnet test --filter "Category=Security" and the equivalents for UI, Functional, Integration, E2E and Regression.
